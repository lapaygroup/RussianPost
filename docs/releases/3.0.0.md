# RussianPost SDK 3.0.0

Основная линия для **PHP ^8.3**, PSR-18/PSR-17. Новый Tracking API выделен в major-релиз; его DTO и ApiKey-контракт не эмулируют прежний SOAP. Остальные провайдеры сохраняют архитектуру 2.0.0. Для PHP 7.4 и прежних Guzzle-конструкторов API 1.x выпускается отдельная версия 1.1.0.

```sh
composer require lapaygroup/russianpost:^3.0
```

Новый `Providers\TrackingApi` использует отдельный ApiKey и REST single. `TrackingResult` сохраняет неизвестные поля/коды и исходные даты, исключает будущие события из `getOperations()` и принимает явный null групп как пустую историю. Ошибки HTTP/transport/SOAP классифицируются без ключей, тел ответов и цепочек исходных исключений.

Новый SOAP batch включается только через `tracking.batch_enabled=true` и остаётся **экспериментальным**. Реализованы независимые пакеты до 3000 РПО, сохранение уже созданных билетов при частичном сбое и DTO результатов; автоматических retries/polling нет. WSDL и live-контракт ещё не приняты, в публичной документации остаётся противоречие ApiKey/login.

Проверка 15.11.2026 с нашей учётной записью и синтетическим ШПИ: single — HTTP 200 и пустая история, новый batch — HTTP 403/auth, прежний batch — HTTP 200 с SOAP ErrorTypeID=3. Билеты не созданы. Это не свидетельство глобального отключения старого SOAP: другие пользователи сообщают о его работе. `Providers\Tracking` сохранён, автоматического переключения между API нет.

`cashOnDelivery` не подтверждает оплату или выплату; аналога прежних финансовых событий в новом API не подтверждено. Миграция потребителя должна учитывать это отдельно.

Автоматическая проверка: PHPUnit, PHPStan level 5, Composer strict; CI PHP 8.3/8.4/8.5. Все fixtures синтетические. Отдельная успешная single-проверка означает только пустую историю, а не приёмку реального отправления или batch.

[Руководство миграции](https://github.com/lapaygroup/RussianPost/blob/3.0.0/docs/tracking-api.md). Существующий tag 2.0.0 не меняется.
